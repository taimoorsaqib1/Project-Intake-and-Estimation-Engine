# Requirements Document

## Introduction

Veloce is an AI-powered project intake and estimation engine for a digital agency. It consists of a public-facing intake form where prospective clients submit project briefs, an AI pipeline that automatically analyzes each brief to extract structured requirements, estimate cost and timeline, and assign a complexity score, and an internal dashboard where the agency team manages briefs through a Kanban pipeline with real-time updates, analytics, and collaboration tools.

## Glossary

- **Brief**: A project submission from a prospective client containing title, description, budget range, timeline urgency, and contact information.
- **AI Analysis**: The structured output produced by the AI pipeline for a given brief, including extracted features, project category, effort estimate, suggested tech stack, and complexity score.
- **Pipeline**: The Kanban-style workflow stages a brief moves through: New → Under Review → Proposal Sent → Won → Archived.
- **Stage Event**: A timestamped log entry recording a brief's transition from one pipeline stage to another.
- **Admin**: A dashboard user role with full access to all briefs, assignments, and system configuration.
- **Reviewer**: A dashboard user role with read access and note-adding capability limited to briefs assigned to them.
- **Complexity Score**: A numeric rating from 1 to 5 assigned by the AI pipeline indicating the estimated technical complexity of a brief.
- **Effort Range**: An estimated range of hours required to complete the project, generated by the AI pipeline.
- **HMAC**: Hash-based Message Authentication Code used to verify the authenticity of webhook payloads.
- **Webhook**: An HTTP POST endpoint that accepts brief payloads from external sources such as Typeform or Zapier.
- **Optimistic UI**: A frontend pattern where the UI reflects a state change immediately before server confirmation.
- **Cursor-based Pagination**: A pagination strategy using a unique cursor (e.g., record ID) rather than numeric offsets.
- **RSC**: React Server Component — a Next.js component that renders on the server with no client-side JavaScript bundle.
- **SSE**: Server-Sent Events — a unidirectional server-to-client streaming protocol for real-time updates.
- **Cache Invalidation**: The process of removing or updating cached data when the underlying data changes.
- **Rate Limiting**: Restricting the number of requests a client can make within a time window.
- **Upstash Redis**: A serverless Redis service used for rate limiting and caching.
- **Neon**: A serverless PostgreSQL provider used as the primary database.
- **Prisma**: An ORM used to interact with the PostgreSQL database.
- **Zod**: A TypeScript-first schema validation library.

## Requirements

### Requirement 1

**User Story:** As a prospective client, I want to submit a project brief through a public form, so that the agency can evaluate my project.

#### Acceptance Criteria

1. THE Intake Form SHALL include fields for project title (text), project description (rich text), budget range (dropdown with predefined tiers), timeline urgency (selectable option), and contact information (name, email).
2. WHEN a user submits the Intake Form with missing required fields, THE Intake Form SHALL display inline validation error messages identifying each missing or invalid field.
3. WHEN a user submits the Intake Form successfully, THE Intake Form SHALL display a confirmation message and clear the form fields.
4. WHILE a form submission is being processed, THE Intake Form SHALL display a loading state and disable the submit button to prevent duplicate submissions.
5. WHEN a user submits the Intake Form more than 5 times within a 10-minute window from the same IP address, THE Rate Limiter SHALL reject the request with an HTTP 429 response and display a user-facing error message.

---

### Requirement 2

**User Story:** As the system, I want to automatically analyze submitted briefs using an AI pipeline, so that structured requirements, estimates, and complexity scores are available without manual effort.

#### Acceptance Criteria

1. WHEN a Brief is successfully submitted, THE AI Pipeline SHALL asynchronously process the brief and produce an AI Analysis record linked to the originating Brief.
2. THE AI Pipeline SHALL extract a structured list of features and requirements from the brief description and store them as part of the AI Analysis record.
3. THE AI Pipeline SHALL classify the project into one of the following categories: Web App, Mobile, AI/ML, Automation, or Integration, and store the classification in the AI Analysis record.
4. THE AI Pipeline SHALL generate an effort range expressed in hours and a suggested tech stack, and store both in the AI Analysis record.
5. THE AI Pipeline SHALL assign a complexity score between 1 and 5 (inclusive) to the brief and store it in the AI Analysis record.
6. IF the AI Pipeline fails to produce a valid structured response after 3 retry attempts, THEN THE AI Pipeline SHALL mark the AI Analysis record with a failed status and log the error for review.

---

### Requirement 3

**User Story:** As an external integration, I want to submit briefs via a webhook endpoint, so that tools like Typeform or Zapier can feed briefs into the same pipeline.

#### Acceptance Criteria

1. THE Webhook Endpoint SHALL accept HTTP POST requests at `/api/webhooks/intake` with a JSON brief payload.
2. WHEN a POST request arrives at the Webhook Endpoint, THE Webhook Endpoint SHALL verify the HMAC signature in the request header before processing the payload.
3. IF the HMAC signature is invalid or missing, THEN THE Webhook Endpoint SHALL reject the request with an HTTP 401 response and not process the payload.
4. WHEN a valid webhook payload is received, THE Webhook Endpoint SHALL process the brief through the same AI Pipeline used for form submissions.
5. THE Webhook Endpoint SHALL apply the same rate limiting rules as the public Intake Form.

---

### Requirement 4

**User Story:** As an agency team member, I want to authenticate with email and password, so that only authorized users can access the internal dashboard.

#### Acceptance Criteria

1. THE Authentication System SHALL support email and password login for dashboard users.
2. WHEN a user provides invalid credentials, THE Authentication System SHALL return an error message without revealing whether the email or password was incorrect.
3. THE Authentication System SHALL enforce two roles: Admin and Reviewer, with role-based access control applied to all dashboard routes and API endpoints.
4. WHILE a user session is active, THE Authentication System SHALL maintain the session and redirect unauthenticated requests to the login page.

---

### Requirement 5

**User Story:** As an Admin, I want to manage briefs through a Kanban pipeline, so that I can track the status of each project opportunity.

#### Acceptance Criteria

1. THE Kanban Board SHALL display briefs organized into the following stages in order: New, Under Review, Proposal Sent, Won, Archived.
2. WHEN an Admin drags a brief card to a new stage, THE Kanban Board SHALL apply an optimistic UI update immediately and persist the stage change to the database.
3. WHEN a brief's stage changes, THE Pipeline SHALL create a timestamped Stage Event record linked to the brief, recording the previous stage, new stage, and the user who made the change.
4. IF a stage change fails to persist, THEN THE Kanban Board SHALL revert the optimistic UI update and display an error notification.
5. THE Kanban Board SHALL be accessible to Admin users only for stage transitions; Reviewer users SHALL view briefs in read-only mode.

---

### Requirement 6

**User Story:** As a dashboard user, I want to view the full detail of a brief alongside its AI analysis, so that I can make informed decisions about the project.

#### Acceptance Criteria

1. THE Brief Detail View SHALL display the original client submission and the AI Analysis side by side.
2. THE Brief Detail View SHALL display the stage timeline showing all Stage Events with timestamps and the user responsible for each transition.
3. THE Brief Detail View SHALL display the assignment history showing which Reviewers have been assigned to the brief.
4. WHEN an Admin assigns a Reviewer to a brief, THE Brief Detail View SHALL record and display the assignment with a timestamp.
5. WHERE a Reviewer is assigned to a brief, THE Reviewer SHALL add notes to the internal notes thread on that brief's detail view.
6. WHEN an Admin or Reviewer submits a note, THE Notes Thread SHALL display the note with the author's name and a timestamp.

---

### Requirement 7

**User Story:** As a Reviewer, I want to override AI-generated estimates on a brief, so that I can apply my own judgment when the AI output is inaccurate.

#### Acceptance Criteria

1. WHEN a Reviewer edits an AI-generated estimate on an assigned brief, THE Brief Detail View SHALL require the Reviewer to provide a reason for the override before saving.
2. WHEN an override is saved, THE AI Analysis record SHALL store the overridden values alongside the original AI-generated values and the reason provided.
3. THE Brief Detail View SHALL visually distinguish overridden estimates from original AI-generated estimates.

---

### Requirement 8

**User Story:** As a dashboard user, I want to see real-time updates when briefs are submitted or stage changes occur, so that I do not need to refresh the page to stay current.

#### Acceptance Criteria

1. WHEN a new Brief is submitted, THE Dashboard SHALL deliver a real-time notification to all connected dashboard users without requiring a page refresh.
2. WHEN a brief's pipeline stage changes, THE Dashboard SHALL update the Kanban Board for all connected dashboard users in real time without requiring a page refresh.
3. THE Real-Time System SHALL use Server-Sent Events, long polling, or WebSockets to deliver updates to connected clients.

---

### Requirement 9

**User Story:** As an Admin, I want an analytics dashboard, so that I can monitor pipeline health and revenue potential at a glance.

#### Acceptance Criteria

1. THE Analytics Dashboard SHALL display a bar chart showing the count of briefs in each pipeline stage.
2. THE Analytics Dashboard SHALL display the average AI complexity score over time as a time-series visualization.
3. THE Analytics Dashboard SHALL display the conversion rate calculated as the ratio of Won briefs to total briefs.
4. THE Analytics Dashboard SHALL display the estimated revenue pipeline calculated as the sum of budget range midpoints for briefs in the New, Under Review, and Proposal Sent stages.
5. THE Analytics Dashboard SHALL display the top project categories by brief count.
6. WHEN a brief's stage changes or a new brief is submitted, THE Analytics Cache SHALL invalidate the cached analytics data and recompute on the next request.

---

### Requirement 10

**User Story:** As a developer, I want the system to follow performance and API best practices, so that the application is scalable, maintainable, and cost-efficient.

#### Acceptance Criteria

1. THE Database Schema SHALL define indexes on all frequently queried fields including brief status, created date, assigned reviewer, and project category.
2. THE API Layer SHALL implement cursor-based pagination for all list endpoints returning brief records.
3. THE API Layer SHALL use Prisma includes and joins to avoid N+1 query patterns on all endpoints.
4. THE API Layer SHALL validate all incoming request payloads using Zod schemas and return a consistent error response format with appropriate HTTP status codes.
5. THE Frontend SHALL use React Server Components for static and data-fetching content and Client Components only where interactivity or browser APIs are required.
6. THE Frontend SHALL display loading skeletons and Suspense boundaries for all asynchronous data-fetching sections.
7. THE Caching Layer SHALL use Upstash Redis to cache analytics query results with a time-to-live of 60 seconds, invalidated on relevant data mutations.
